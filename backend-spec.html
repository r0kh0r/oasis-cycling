01 · Overview

What the backend has to do

The business objective is e-mail capture with marketing consent, so the heavy lifting happens once — at signup. Everything after that exists to keep users engaged (predictions) and to give the marketing team a warm, relevant reason to email them (race results → Privana upsell).

The backend has exactly five responsibilities:

  1. Onboard — verify an email (OTP), capture marketing consent, and provision a Turnkey embedded wallet that becomes the user's durable account (it carries over to Privana later).
  2. Mint the signup ticket — one raffle ticket the moment the account exists.
  3. Run predictions — store a ranked podium (1st / 2nd / 3rd) per contest, editable until 24h before the race starts.
  4. Resolve & reward — when a race finishes, record the podium and award +1 ticket per place each user called exactly right, then trigger the result email.
  5. Draw — at the season's end, pick 10 winners weighted by ticket count.
💡
Design principle: tickets are the only state that matters, and they can only be created server-side (signup + correct prediction). No payments, no leaderboard, no scoring. That keeps the surface tiny and the sweepstakes clean ("no purchase necessary").

Assumptions

  • Frontend is the existing static index.html (lander) + portal.html, talking to Supabase via supabase-js with the anon key.
  • Supabase provides Postgres, Auth (email OTP), PostgREST, Edge Functions (Deno), and pg_cron.
  • Turnkey is called only from Edge Functions (server-side keys), never the browser.
  • Transactional email via Resend (or Postmark) — interchangeable.
  • Five contests for v1: the Tour de France, plus the men's and women's World and European Championships.

Client never holds secrets

The browser uses only the Supabase anon key + the user's JWT. All privileged work (Turnkey, ticket minting, resolving, drawing) lives in Edge Functions using the service role key.

Reads are cheap, writes are guarded

Public reads (contests, riders) and own-row reads/writes (predictions) go straight through PostgREST + RLS. Only the two trust-sensitive actions — onboarding and admin — need Edge Functions.

05 · Auth & Turnkey

Supabase owns identity, Turnkey owns the wallet

The cleanest minimal split: Supabase Auth handles the email OTP (the code in the signup modal is the Supabase OTP), giving you sessions and RLS for free. Turnkey is provisioned server-side on first login and produces the wallet that becomes the user's Privana account.

  1. Frontend calls supabase.auth.signInWithOtp({ email }) → user receives the 6-digit code.
  2. Frontend calls supabase.auth.verifyOtp({ email, token }) → returns a session.
  3. Frontend calls POST /onboard (with the session JWT). The Edge Function:
    • creates a Turnkey sub-organization + wallet for the user (idempotent — keyed on user_id),
    • upserts profiles with wallet + marketing_consent + consent_at,
    • inserts the signup ticket (ON CONFLICT DO NOTHING).
⚙️
Alternative: Turnkey can also run the email auth itself (Turnkey Auth / passkeys) and you mint a Supabase session from a custom JWT. That removes one email step but adds a custom-token exchange — heavier than the MVP needs. Recommend the Supabase-OTP path above and revisit only if you want passkeys.
🔁
Idempotency: /onboard may be called more than once (refresh, retry). Look up profiles.turnkey_sub_org_id first; if present, skip provisioning and just return current state. The unique constraint on the signup ticket prevents double-minting.

06 · API reference

Two surfaces

Most of the app is plain PostgREST + RLS (auto-generated REST). Only trust-sensitive actions are custom Edge Functions. Base URLs:

REST   https://<project>.supabase.co/rest/v1
EDGE   https://<project>.supabase.co/functions/v1

All requests send apikey: <anon>. Authenticated calls add Authorization: Bearer <user-jwt>. Admin calls add Authorization: Bearer <admin-jwt> (or an x-admin-secret header).

Public reads — PostgREST

GET/rest/v1/contests?select=*,riders(*)&order=starts_atanon

All contests with their riders, status and (once set) the winner. Drives both the landing teaser and the portal cards.

The caller's own podium picks, 3 rows per predicted contest (RLS filters to user_id = auth.uid()).

POST/rest/v1/predictionsuser

Save or change a podium — upsert the 3 rows on the (user_id, contest_id, position) key. Header Prefer: resolution=merge-duplicates.

POST /rest/v1/predictions          // user_id is set by a DB default = auth.uid()
[ { "contest_id": "…", "position": 1, "rider_id": "…" },
  { "contest_id": "…", "position": 2, "rider_id": "…" },
  { "contest_id": "…", "position": 3, "rider_id": "…" } ]

201 Created   // or rejected 4xx if picks are closed (see trigger)
🔒
A BEFORE INSERT/UPDATE trigger rejects the write unless contest.status = 'open' and now() < contest.picks_close_at (i.e. more than 24h before the start). The deadline is enforced in the database, not the client — so the frontend's "edit until …" label and the server agree.

Ticket count — PostgREST view

GET/rest/v1/v_my_ticketsuser

Returns one row: { tickets, from_signup, from_predictions } for the caller.

Onboarding — Edge Function

POST/functions/v1/onboarduser

Called once after verifyOtp. Provisions the Turnkey wallet, writes the profile + consent, mints the signup ticket. Idempotent.

{ "marketing_consent": true, "country": "SI" }

200 OK
{ "wallet_address": "0xA3…b91f", "tickets": 1, "is_new": true }

Admin — Edge Functions

POST/functions/v1/admin/contests/{id}/resolveadmin

Record the finishing podium, flip status to resolved, award +1 ticket for every place a user predicted exactly right (one transaction), and enqueue the result emails.

POST /functions/v1/admin/contests/{id}/resolve
{ "podium": ["rider_id_1st", "rider_id_2nd", "rider_id_3rd"] }

200 OK
{ "status":"resolved", "tickets_awarded": 3120, "predictors_emailed": 4217 }
✅
For each position, award a ticket to users whose predictions(contest,position).rider_id matches the result, via INSERT INTO tickets … ON CONFLICT DO NOTHING — so re-running resolve never double-awards.
POST/functions/v1/admin/contests/{id}/lockadmin

Manually freeze picks (also done automatically by cron at picks_close_at). Sets status='locked'.

POST/functions/v1/admin/drawadmin

Weighted random draw at campaign end. Each ticket is one entry; draw 10 distinct users; write winners. Uses a seeded RNG and logs the seed for auditability.

POST /functions/v1/admin/draw
{ "prizes": ["Colnago V4Rs","Signed jersey + helmet","Signed jersey","Helmet","Jersey","Jersey","Jersey","Jersey","Jersey","Jersey"], "seed": "optional" }

200 OK
{ "seed":"…", "winners":[{ "prize_rank":1, "user_id":"…", "tickets":3 }, …] }
GET/functions/v1/admin/export?consent=trueadmin

CSV of consented emails for the marketing platform (the campaign's actual deliverable). Filterable by consent, country, activity.

08 · Email / notification pipeline

The warm-email engine

This is where the campaign pays off: a race result is a non-cold reason to land in the inbox, and Privana rides along as the upsell.

  • Transactional (triggered): OTP code (Supabase Auth), "you're in" welcome, and the result email fired by resolve — "You called the Tour podium! +2 tickets" / "Here's the podium + your standing", each carrying a Privana CTA.
  • Marketing (broadcast): sent from your ESP to the marketing_consent = true segment exported via /admin/export. Kept separate from transactional so consent and deliverability stay clean.

Implementation: resolve writes rows to an email_outbox table; a small Edge Function (or cron) drains it through Resend with a templated payload. Decoupling the send keeps resolve fast and retry-safe.

09 · Security & RLS

  • RLS on every user table. profiles, predictions, tickets, winners: a user can read only user_id = auth.uid(). contests + riders are world-readable (anon select), write denied.
  • Tickets are server-minted only. No insert/update/delete policy for clients on tickets — they appear only via Edge Functions using the service role. This is what keeps odds honest.
  • Lock enforced in the DB via the predictions trigger, so a crafted client request can't sneak a late pick.
  • Service role key never leaves Edge Functions. The browser only ever has the anon key + the user JWT.
  • Admin gating: admin Edge Functions check an admin claim / allowlisted email, or a shared x-admin-secret. Keep the admin console off the public domain.
  • Idempotency & audit: unique constraints make onboarding and awards safe to retry; the append-only tickets ledger and the logged draw seed make the outcome auditable.
  • OTP abuse: rely on Supabase Auth rate limits; optionally add a per-IP throttle on /onboard.
  • Sweepstakes hygiene: no payment path exists, so "no purchase necessary" holds by construction. One-account-per-person enforcement (email is the natural key) is a known soft spot — flag duplicate detection as a fast-follow if abuse appears.

11 · MVP scope

What to build now vs. later

✅ In scope (v1)

  • Supabase email OTP + /onboard (Turnkey wallet, consent, signup ticket)
  • contests + riders seed data (5 races, men's & women's)
  • Predictions upsert with DB-enforced lock
  • Tickets ledger + v_my_tickets view
  • Admin resolve (winner + award + email) and draw
  • Consented-email CSV export
  • RLS, cron lock job, transactional email

⏳ Deferred

  • Real-time updates (poll/refresh is fine at this scale)
  • Leaderboards / scoring (intentionally removed)
  • Payments, KYC, on-chain actions (none needed to enter)
  • Passkeys / Turnkey-native auth
  • Duplicate-account / fraud detection
  • Multi-language, rider photos/CDN, admin analytics
🧭
Build order: (1) tables + RLS + seed, (2) Supabase OTP wired into the existing modal, (3) /onboard + Turnkey, (4) predictions read/write, (5) ticket view bound to the portal counters, (6) admin resolve + email, (7) draw. Steps 1–5 make the frontend fully live; 6–7 are operational and can land before the first race concludes.
